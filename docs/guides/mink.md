# Differential IK (URLabMink)

`URLabMink` is a 1:1 C++ port of [mink](https://github.com/kevinzakka/mink) v1.2.0, the
differential inverse-kinematics library by Kevin Zakka and contributors, built on MuJoCo. Full
credit for the algorithms, task/limit taxonomy, and API design in this module belongs to the
upstream project — this port only translates it to Eigen/MuJoCo C++ for use inside Unreal, and
adds a small number of deliberate deviations documented below.

The port is pinned to mink `v1.2.0` (commit `198674e30efcd8ffe24b58155c60abc014198b9f`) and
targets `mujoco==3.9.0` on the Python side. Every layer (lie group math, `Configuration`, tasks,
limits, the QP solve) is checked against golden vectors generated by running the real Python
library, so numerical behaviour tracks upstream mink at that exact pin rather than a
best-effort re-implementation.

URLabMink has no dependency on URLab; `URLab` consumes it as a normal private module
dependency so future components (e.g. an end-effector controller or VR teleop) can
`#include "MinkSolveIK.h"` and friends directly.

## Usage example

```cpp
#include "MinkConfiguration.h"
#include "MinkSolveIK.h"
#include "Tasks/MinkFrameTask.h"
#include "Tasks/MinkPostureTask.h"

// `Model` is an mjModel* you already own (e.g. from an FMujocoSpecWrapper compile).
void SolveToTarget(const mjModel* Model, const FMinkSE3& TargetPose)
{
    // Configuration owns its own mjData and runs forward kinematics on construction.
    FMinkConfiguration Configuration(Model);

    // Primary task: drive the "end_effector" site to a target pose in the world frame.
    FMinkFrameTask EndEffectorTask(TEXT("end_effector"), EMinkFrameType::Site,
        FMinkVec::Constant(1, 1.0),  // position cost, broadcast to (x, y, z)
        FMinkVec::Constant(1, 1.0)); // orientation cost, broadcast to (rx, ry, rz)
    EndEffectorTask.SetTarget(TargetPose);

    // Secondary task: bias the redundant nullspace towards the current posture.
    FMinkPostureTask PostureTask(Model, FMinkVec::Constant(1, 1e-2));
    PostureTask.SetTargetFromConfiguration(Configuration);

    const TArray<const FMinkBaseTask*> Tasks = { &EndEffectorTask, &PostureTask };
    constexpr double Dt = 1.0 / 60.0;

    // Passing nullptr for Limits defaults to a single FMinkConfigurationLimit(Model), mirroring
    // mink's own default when solve_ik() is called with limits=None.
    for (int32 Iter = 0; Iter < 100; ++Iter)
    {
        const FMinkIKResult Result = MinkSolveIK(Configuration, Tasks, Dt);
        if (!Result.IsSuccess())
        {
            break; // EMinkIKStatus carries NoSolutionFound / TaskError / LimitError / etc.
        }
        Configuration.IntegrateInplace(Result.Velocity, Dt);
    }
}
```

## Parity testing

Numerical parity with Python mink is enforced by golden-vector automation tests
(`URLab.Mink.*`), not just structural translation. `Scripts/mink_golden/` holds the fixture
generator:

- `gen_golden.py` imports the pinned Python `mink` package and MuJoCo models under
  `Scripts/mink_golden/models/`, and dumps one JSON fixture per layer to
  `Scripts/mink_golden/fixtures/` (lie ops, `Configuration`, each task, each limit, the QP
  solve, and end-to-end `solve_ik`). Every case stores its inputs explicitly; randomness only
  ever runs inside the generator, seeded, so replay is deterministic.
- The C++ tests load those committed fixtures and assert `MaxAbsDiff(a, b) <= Tol * Max(1,
  MaxAbs(b))` against the tolerances used throughout the port (`1e-10` for lie ops down to
  `1e-6` for end-to-end `solve_ik`).

To set up the generator and regenerate fixtures:

```bash
cd "Scripts/mink_golden"
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Regenerate everything, or just one layer:
python gen_golden.py
python gen_golden.py --layers lie
```

`fixtures/` and `requirements.lock` are committed so the C++ tests run without a Python
environment; `.venv/` is not. Fixtures are pinned to mink v1.2.0 and mujoco 3.9.0 — regenerating
against a different version invalidates parity and must come with a corresponding port update.

## Deliberate deviations from Python mink

These are the only intentional differences from upstream mink's behaviour:

1. **Exceptions become status, not throws.** Python's exceptions are replaced with `bIsValid`
   flags set at construction and `bool` / status-enum returns on hot paths, each logging the
   exact Python exception message text via `UE_LOG(LogURLabMink, ...)`.
2. **No abstract `MatrixLieGroup` base.** Python's dataclass-style shared base for `SO3`/`SE3`
   isn't ported; both are standalone structs exposing the same method set.
3. **`SampleUniform` takes an explicit `FRandomStream&`** instead of relying on a global RNG,
   and is excluded from the parity fixtures for that reason.
4. **`FMinkVelocityLimit` takes an ordered `TArray<TPair<FString, FMinkVec>>`**, not a map, to
   preserve Python-dict insertion order, since that order fixes the row order of `G`.
5. **`FMinkCollisionAvoidanceLimit` sorts deduped geom-id pairs ascending** on both the C++ and
   fixture-generator sides, since Python's `list(set(...))` pair order is not reproducible
   across runs.
6. **`contrib/keyboard_teleop` is not ported** — it's specific to the MuJoCo interactive viewer,
   which URLab doesn't use.

Two additional deviations were needed purely for the JSON fixture format, not the C++ port
itself:

7. **The QP fixture's inequality bound is stored under the key `"h_ineq"`, not `"h"`.**
   `FJsonObject`'s keys are `FString`-hashed, and `FString::GetTypeHash` / `operator==` are
   case-insensitive, so a field named `"h"` would collide with `"H"` (the Hessian) and silently
   clobber it when read back on the C++ side.
8. **Infinite values are string-encoded as `"Infinity"` / `"-Infinity"`.** `json.dumps` happily
   emits the bare tokens `Infinity` / `-Infinity` for non-finite floats, which are not valid
   strict JSON and break `FJsonSerializer::Deserialize` for the whole file. The only place real
   infinities occur is the collision-avoidance limit's `h` vector (skipped-row sentinel), so the
   generator encodes those two values as strings and the C++ JSON helpers (`MinkJsonVec` /
   `MinkJsonMat`) special-case them back to `+`/`-infinity`.
